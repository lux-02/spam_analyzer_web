저작권 사칭 메일에서 시작해 서명된 Word 실행 파일과 악성 DLL을 함께 배포하는 체인이 정적 분석으로 확인됐습니다. 서명 유효성에만 의존하지 않고 실행 위치·원래 파일명·인접 DLL·지속성 흔적을 결합해 점검해야 하며, 아래 내용은 실행 관찰이나 실제 정보 유출을 입증한 결과가 아닙니다.

## 핵심 사실

- **메일 인증과 사칭 여부는 별도 판단이 필요합니다.** 2026년 10월 19일 06:32 KST에 국내 기업이 수신한 메일은 기업명을 넣은 저작권 철회 요청을 내세웠고, 표시 이름에는 실존 PR사를 사용했습니다. 실제 발신 계정은 `blaisebotjasted8@gmail[.]com`이었으며 SPF·DKIM·DMARC 결과는 모두 pass였습니다. 이는 Gmail 발신 경로의 인증과 표시 이름에 적힌 기업의 신원을 구분해야 하는 사례입니다. 본문은 48시간 기한과 법률 문구를 사용했고, 숨긴 미리보기 텍스트로 긴급성을 강조했습니다. 수신 기업 정보가 맞는다는 사실도 발신자의 권한을 입증하지 않습니다. 원문에서는 추적 픽셀이나 수신자별 토큰을 찾지 못했다고 기록했습니다. 게이트웨이 검토에서는 인증 실패만 찾기보다 기업 표시 이름·무료 메일 계정·외부 증거 다운로드·기한 압박의 조합을 확인할 필요가 있습니다.
- **웹 단계는 이용 환경을 선별하고 압축 파일을 전달했습니다.** 메일 링크는 Google Sites의 임베드 페이지로 이어졌습니다. 로봇 확인을 흉내 낸 체크 상자는 실제 인증 없이 약 2.2초 뒤 `download[.]foden[.]site`의 zip 다운로드를 시작하도록 작성돼 있었습니다. 모바일 User-Agent 또는 작은 터치 화면에는 실패 화면과 PC 접속 안내가 표시됐고, 배포 서버 역시 데스크톱 요청과 모바일 요청에 서로 다른 응답을 보였습니다. 따라서 모바일에서 페이지가 실패하거나 파일을 받지 못하는 현상만으로 유포 종료를 판단하기 어렵습니다. 분석 당시 페이지에는 개발자 도구 단축키 차단과 반복적인 debugger 구문도 있었습니다. 배포 서버가 응답했다는 마지막 기록은 2026년 10월 19일 08:52 UTC이며, 이 요약에서 현재 서버 상태를 재확인한 것은 아닙니다. Google 서비스의 정상 도메인과 그 안에서 연결하는 외부 다운로드의 신뢰도를 나눠 봐야 합니다.
- **압축 내부의 세 파일은 위장·로딩·크기 부풀리기를 나눠 맡았습니다.** zip 크기는 189,691,188바이트였습니다. 실행 파일은 Office 2013 계열 `WINWORD.EXE`를 가져와 `.docx` 뒤에 약 100자의 공백과 `.exe`를 붙인 이름으로 바꿨습니다. 같은 폴더에는 악성 `msvcr100.dll`과 무작위 데이터로 채운 `.tmp`가 들어 있었습니다. DLL은 52,428,800바이트로 늘려져 있었지만 실제 코드는 약 224KB였고, 패딩용 `.tmp`는 188,743,680바이트였습니다. 압축 안 파일 크기의 합과 zip 크기를 혼동하지 않아야 합니다. Word 실행 파일은 실행 시 인접한 가짜 DLL을 불러오는 호스트 역할을 합니다. 이 조합은 정상 서명 파일 단독 허용, 파일 이름 앞부분만 확인하는 검수, 대용량 파일 검사 생략 정책의 빈틈과 관련됩니다. 크기 부풀리기의 목적은 분석자의 해석이며, 특정 보안 제품을 실제 우회했는지는 실행 검증하지 않았습니다.
- **2단계는 서명 호스트의 인증서 테이블에서 꺼내도록 구성됐습니다.** 분석자는 `WINWORD.EXE`의 인증서 테이블에 덧붙인 블록과 `SIGI` 표식을 찾았고, 로더의 복호화 처리를 따라가 .NET 어셈블리를 확보했습니다. 서명이 유효하게 표시되면서 추가 데이터가 함께 존재한 사례로, 원문은 이를 CVE-2013-3900 유형으로 설명합니다. 이 파일의 SHA-256은 `e991a13a2baefd946264fe2e656d2fd1c4539f2b3bcf1c72f7e10064c61a37bc`입니다. 인증서나 Authenticode 해시 대조만으로 원본과 추가 데이터 포함 파일을 구별하지 못할 수 있어, 파일 전체 해시를 따로 확인해야 합니다. 원문의 서명 패딩 검사 설정은 서명 신뢰 판단을 강화하는 조치이며, 그 설정만으로 실행을 차단한다는 의미는 아닙니다. 인증서 테이블 크기와 표식 조합 역시 헌팅 조건으로 다뤄야 합니다. 정상 파일에도 큰 인증서 영역이 있을 수 있으므로 크기 하나만으로 악성 판정을 내려서는 안 됩니다.
- **로더에는 지연·지속성·프로세스 주입 관련 코드가 있습니다.** `msvcr100.dll`은 `SysCacheData_4A8F` 뮤텍스, 물리 메모리 3GB 이하 종료 조건, 첫 실행의 315초 지연과 시간 가속 감지 처리를 포함했습니다. `%APPDATA%\SystemDiagnostics\werfaultsvc.exe` 설치 경로와 Run 값 `SysCacheService`, CLSID `{89565275-A714-4a43-912E-978B935EDCCC}`의 `InprocServer32` 변경도 분석 대상입니다. 문자열에는 XOR 난독화가 적용돼 있고 AMSI·ETW 패치를 위한 참조가 확인됐습니다. 이후 `cvtres.exe`, 대체 경로로 `msiexec.exe`를 일시정지 생성해 섹션을 매핑하는 코드로 연결됩니다. 이들은 실제 단말에서 관찰한 타임라인이 아니라 정적 분석에서 복원한 실행 흐름입니다. 탐지 시에는 Windows 구성 요소처럼 보이는 경로명 자체보다 파일 생성, 레지스트리 변경, 부모·자식 프로세스의 관계를 함께 확인해야 합니다. 일부 흔적만 없다고 전체 체인을 배제할 수는 없습니다. 원문에는 명명 파이프 `EnvironmentTelemetryPipe`와 `__DLL_PIPE_COMPLETION_SIGNAL__`, `HVNC_MailMaster`, `LXClipMon` 같은 문자열도 제시돼 있습니다. 단일 문자열 일치만으로 차단하기보다 관련 파일·메모리·프로세스 흔적을 좁히는 단서로 사용할 수 있습니다. 반대로 이 지표가 없다는 이유만으로 다른 이름을 쓰는 변종까지 탐지했다고 볼 수는 없습니다.
- **최종 페이로드의 기능과 C2 연결 성공은 구분해야 합니다.** 복호화된 어셈블리는 `LX_PYLD_7A5D4A91`이며 내부 이름과 문자열을 따라 LXBASE라고 부릅니다. 브라우저 자격 증명과 쿠키 수집, 메일·메신저 정보 접근, HVNC, 지갑 탐색, 클립보드 주소 교체, 웹캠·마이크 관련 기능이 코드에 포함돼 있었습니다. C2 주소는 GitHub의 `redteam1337/project_notes` 저장소 `readme.md`에서 읽는 구조로 분석됐습니다. 해당 계정과 저장소는 2026년 10월 19일 삭제된 것으로 확인돼 실제 C2 주소를 확보하지 못했습니다. 명령 프로토콜, 실제 유출 데이터, 원격 조작 성공 여부도 검증하지 않았습니다. 저장소 삭제는 분석 당시 주소 획득 경로에 관한 정보이며 감염 부재나 변종의 무해성을 입증하지 않습니다. 공개 위협 정보의 패밀리 명명과 대조하지 않았으므로 LXBASE를 확정된 상용 탐지명처럼 사용하거나, 유사한 저작권 사칭 캠페인과 같은 공격자로 묶어서도 안 됩니다.
- **IOC와 규칙은 검증 수준에 맞춰 적용해야 합니다.** 로더 SHA-256은 `17e6afb8b8a54192d3786e2115d34679086f2863721e92065f49db2d65baa169`, 복호화한 .NET 파일은 `9499c3eebf3173d643f949fa4e5b0cdb480abf74bee2c329fa9ea589dea0e1d7`입니다. 네트워크 지표는 `foden[.]site`와 `download[.]foden[.]site`이며, 앞단 Cloudflare 공유 IP를 이 사건 전용 인프라로 취급해서는 안 됩니다. 원문의 YARA 규칙은 YARA 4.5.8에서 샘플 3개 탐지와 정상 PE 24개 오탐 0을 확인한 수준입니다. 운영 환경에서 오탐이 없다는 보증이 아니므로 정상 파일 대조군을 늘려 재검증해야 합니다. Sigma 두 규칙은 실제 이벤트 로그로 검증하지 않은 초안입니다. 특히 첫 실행 파일의 이름이 바뀌어 있으므로 `Image`가 `WINWORD.EXE`로 끝나는 조건만으로는 누락될 수 있습니다. `OriginalFileName` 보완 역시 원문에서 제안한 사항이며, 로그 수집 여부와 필드 매핑을 확인한 뒤 검증해야 합니다. 부모 프로세스 역시 위장된 실행 파일명을 사용할 수 있으므로 자식 쪽 이름 조건만 보완하는 것으로는 충분하지 않습니다. 원문의 전체 규칙과 예외 조건을 함께 읽고, 사내 정상 Office 실행 및 개발 도구 사용 로그와 비교하는 과정이 필요합니다. 해시 일치는 이 샘플 확인에 유용하지만 파일이 바뀌면 값도 달라지므로, 해시 검색 결과와 행위 탐지의 범위를 구분해 기록해야 합니다.

## 할 일

1. **메일·웹 구간의 지표부터 조회하고 필요한 차단을 적용합니다.** 위 도메인과 발신 계정을 메일·DNS·프록시 기록에서 검색하고, 다운로드 시각과 사용자·단말을 연결하세요. 조사 대상 URL은 보안 도구에서 취급하며 일반 브라우저로 열어 상태를 확인하지 마세요. Google Sites 전체나 Cloudflare 공유 IP의 일괄 차단보다는 사건 지표와 실제 조직 트래픽을 기준으로 범위를 정하고, 파일 크기 제한으로 검사를 생략한 다운로드도 조사 대상으로 포함하세요.
2. **파일명 대신 실행 맥락과 지속성 흔적을 묶어 헌팅합니다.** Office 밖의 Word 원래 파일명, 인접한 `msvcr100.dll`, 위 설치 경로와 Run 값·CLSID, 의심스러운 `cvtres.exe` 부모 관계를 교차 확인하세요. 정적 규칙은 정상 파일과 실제 로그를 이용해 검증한 뒤 적용하고, 원문의 YARA·Sigma를 검증 완료된 운영 규칙으로 취급하지 마세요. 서명 패딩 검사 설정도 조직의 허용 정책과 호환성을 점검하는 시범 적용부터 검토하세요.
3. **실행 정황이 있으면 단말 격리와 계정 보호를 함께 진행합니다.** 원문 메일·다운로드 기록·프로세스 및 레지스트리 증거를 보존하고 대응 담당자에게 넘기세요. 비밀번호 교체에 더해 깨끗한 기기에서 활성 세션을 종료하며, 지갑·결제 정보 노출 여부도 조사하세요. 여러 지속성 경로가 분석된 만큼 파일 하나를 삭제한 뒤 끝내지 말고 단말 재설치를 포함한 복구 범위를 결정하세요.
4. **사내 공유 시 분석 범위와 시점을 붙입니다.** 근거는 macOS 환경의 정적 분석이며 악성 파일 실행, VirusTotal 평판 조회, C2 연결 및 유출 확인은 수행하지 않았습니다. 저장소 삭제와 서버 응답은 2026년 10월 19일 확인 기록으로 인용하고 현재 상태와 구분하세요. 특히 코드에 기능이 존재한다는 사실, 그 기능이 실행됐다는 사실, 그 결과 피해가 발생했다는 사실을 조사 기록에서 각각 분리하세요. 이 보고서는 첫 번째에 대한 자료이며 나머지는 단말과 계정 로그 등 별도 증거가 필요합니다. 원문에 제시된 다른 캠페인과의 공통점은 수법 비교이며, 동일 행위자·동일 패밀리라는 귀속 근거로 사용하지 마세요.
